We provide the fixed cases in the train, dev and test dataset.
```
.
|-- raw/    # Json files of original datasets
|-- opt/    # Json files of fixed datasets
  |-- train.json                # Train set data
  |-- train_sampled_fix.json    # Comparison before and after fix
  |-- ...
|-- schemas/    # files of schema definition of each application
```

The files with postfix '_fix' presents the modified cases only.
SQL queries of the key 'original' and 'fixed' represent the original and fixed SQL queries, respectively.
The key 'note' of each case briefly describe the error type.

Note that in the train dataset, not all (but most) cases are guaranteed to be fully correct since they are automatically fixed by our tool and a few miscorrections inadvertently happen. 
We did not manually check all the training cases due to time limitation, and provide correct fix and detailed information for 500 sampled training cases instead.
Despite that, the train dataset owns better quality than original and fine-tunes models to get higher accuracy on our test dataset.

Besides, we also fix a few flaws in schema definitions (e.g., lack of foreign key definition) and provide the schema definition files.

### Notes
Here are some frequent common types appeared in the dataset:
 - **'join -> left join'**: incorrectly use INNER JOIN for aggregation like counting. LEFT JOIN should be used to preserve records whose corresponding count is 0, since the natural language query usually asks for 'show ... for **EACH** xxx'. 
 - **'join -> in-sub'**: JOIN operators would inadvertently incur duplicated records in the result set (e.g., the name and age of one student are shown multiple times in the result). Rewrite JOIN to IN-subquery can avoid this issue.
 - **'group by non-key', 'intersect / except non-key', 'distinct non-key'**: The non-key attributes are used in GROUP BY, INTERSECT / EXCEPT, or DISTINCT operators in aggregation, which does not consider the impact of duplication on non-key attributes to the query result.
 - **'limit 1 / n'**: 'limit 1' or 'limit n' operator drops ties when retrieving records with top-1/top-n values. 'WHERE col  = (SELECT max() ...)' or 'RANK OVER() = 1' should be applied to preserve ties. Gold SQL with 'limit 1' that excludes ties even cause misjudgements of SQL prediction correctness: if the predicted SQL returns another top-1/top-n record, it is also correct but is judged incorrect under Execution Accuracy metric.
 - **'semantic error'**: other case-specific types.

### Evaluation Metric
When using *Execution Accuracy* metric (1 sqlite instance for execution), non-equivalent gold SQL and prediction SQL could return the same execution result on this instance, which incurs misjudgements of prediction correctness.
For example, SQL queries with INNER JOIN and LEFT JOIN mentioned above could return the same result on a specific instance, but they are not equivalent in general.

So we prefer to use *Test Suite Accuracy* metric (multiple sqlite instances generated by fuzzing, [link](https://github.com/taoyds/test-suite-sql-eval)) to precisely evaluate model accuracy with much fewer misjudgements.
